四、常用调试/监控指令
================================================================================

【查看飞控连接状态】
  描述: 查看 MAVROS 是否连接上 PX4，以及当前飞行模式、解锁状态
  rostopic echo /mavros/state

【查看无人机实时位置】
  描述: 查看无人机在本地坐标系下的 x,y,z 位置
  rostopic echo /mavros/local_position/pose

【查看 IMU 数据】
  描述: 查看加速度计和陀螺仪数据，确认传感器工作正常
  rostopic echo /mavros/imu/data

【查看所有 MAVROS 话题】
  描述: 列出 MAVROS 发布的所有话题
  rostopic list | grep mavros

【手动切换飞行模式】
  描述: 通过命令行切换 PX4 飞行模式
  rosservice call /mavros/set_mode "custom_mode: 'OFFBOARD'"
  rosservice call /mavros/set_mode "custom_mode: 'AUTO.LAND'"
  rosservice call /mavros/set_mode "custom_mode: 'AUTO.RTL'"
  rosservice call /mavros/set_mode "custom_mode: 'POSCTL'"

【手动解锁/锁定电机】
  描述: 解锁或锁定无人机电机
  rosservice call /mavros/cmd/arming "value: true"
  rosservice call /mavros/cmd/arming "value: false"

【查看 Gazebo 模型列表】
  描述: 查看 Gazebo 中当前加载的所有模型
  gz model --list

【查看 ROS 节点图】
  描述: 用图形方式查看 ROS 节点通信关系
  rqt_graph

【查看 TF 树】
  描述: 查看坐标系变换关系
  rosrun tf view_frames && xdg-open frames.pdf

================================================================================
第四次操作 - Bug修复 + 功能增强
================================================================================

【本次修复了以下问题】

问题1: navigation.launch 加载地图后 octree 为空
  原因: octomap_server_node 没有收到 .bt 文件参数, 地图未被加载
  修复: navigation.launch 中给 octomap_server 添加 args="$(arg map_file)"

问题2: RViz 中相机图像显示 "No Image" + TF报错
  原因: SDF传感器缺少 <always_on> 标签; TF中MAVROS帧与Fast-LIO帧不通
  修复: 
    - 无人机SDF添加 <always_on>true</always_on> 和 <visualize>false</visualize>
    - 相机降至15fps减少WSL2 GPU负载

========== 发现的问题和修复 ==========

问题1: 无人机不起飞 (桨叶转但不升空)
  根因: PX4 OFFBOARD模式要求: 进入OFFBOARD前必须已连续接收setpoint ≥2秒
        旧代码发送了20帧(1秒)当前位置(z=0)的setpoint, 然后切OFFBOARD+ARM
        → PX4收到的目标高度是0 (地面) → 不爬升
  修复: 新增 PRE_ARM 阶段:
        ① 先持续发送"目标巡检高度"的setpoint 2.5秒
        ② 然后切OFFBOARD + ARM
        ③ 新增 TAKING_OFF 阶段等待爬升到目标高度
        ④ 到达高度后才开始执行巡检航线

问题2: 只能标定障碍物表面, 无法在3D空间任意标点  
  根因: RViz的Publish Point发射射线击中最近的可见表面(OctoMap方块)
        → 标点只能落在障碍物上 → 无人机飞去撞障碍物!
  修复: 彻底改为2D标点方案:
        ① 点击只取x,y坐标, 完全忽略z
        ② z由用户通过终端设定: alt 2.0
        ③ RViz视角改为近乎俯视(Pitch=1.3), 便于鸟瞰标点
        ④ 淡蓝色半透明平面显示巡检高度

问题3: RRT*算法不稳定, 经常"未找到路径, 使用直线"
  替换: RRT* → A* (确定性2D网格搜索)
        ① 从3D OctoMap提取指定高度的2D障碍物切片 (±1m范围)
        ② 2D A* 8方向搜索 + 安全膨胀
        ③ 路径简化(去除A*中间冗余步进点)
        结果: 100%确定性找到路径, 速度远超RRT*

========== 问题2: 大地图OctoMap彩色方块消失 ==========

原因分析:
  - 之前使用 rviz/MarkerArray 显示 /occupied_cells_vis_array 话题
  - OctoMap服务器将每个体素作为一个单独的Marker发布
  - 大地图体素数量巨大(几十万个), MarkerArray消息太大导致:
    a) RViz渲染不过来 → 彩色方块消失
    b) 网络带宽不够 → 消息丢失
    c) 只剩下Fast-LIO2的点云能显示

修复方案:
  - 使用 octomap_rviz_plugins 原生 OctoMap 显示插件
  - 插件类: octomap_rviz_plugin/OccupancyGrid
  - 订阅话题: /octomap_binary (OctoMap二进制消息, 比MarkerArray小得多)
  - 原理: 直接读取八叉树二进制数据进行GPU渲染, 无需转换为MarkerArray
  - 效果: 即使地图很大, 也能流畅显示彩色体素

修改文件:
  1. config/slam_mapping.rviz
     - OctoMap显示: MarkerArray → octomap_rviz_plugin/OccupancyGrid
     - 话题: /occupied_cells_vis_array → /octomap_binary
  2. config/navigation.rviz
     - 同上替换 OctoMap 显示方式
     - 新增 Drone_Position 显示
  3. scripts/patrol_planner.py
     - 新增 _publish_drone_marker() 方法
     - 主循环 run() 中 ~5Hz 调用

【问题2: OctoMap大地图彩色方块消失 ★★★ 核心修复】
  现象: 建图初期OctoMap正常显示, 飞行一段时间后彩色方块完全消失
        (第十次修复了nan_filter性能后, 问题依旧)
  根因: 问题不在SLAM, 而在OctoMap Server本身!
        OctoMap八叉树插入复杂度为 O(n log n), n=节点数
        → 当八叉树增长到百万节点时, 每帧插入耗时 > 100ms
        → 10Hz输入 → 处理跟不上 → 队列溢出 → OctoMap停止更新
        
        量化分析:
        - Mid-360输出: 11520点/帧 × 10Hz = 115k点/秒
        - 分辨率0.10m + max_range=30m → 八叉树最大约550万节点
        - 10Hz下每帧只有100ms, 大八叉树插入远超此限
        
  修复 (三管齐下, 共降低~17倍负载):
    1. 时间降频: topic_tools/throttle 将cloud_filtered从10Hz降到2Hz (5倍)
       → 每帧有500ms处理时间, 足以应对百万级八叉树
    2. 空间降采样: OctoMap分辨率 0.10m → 0.15m (约3.4倍节点减少)
    3. 范围限制: max_range 30m → 20m (减少每帧需插入的点数)
    
  为什么不换SLAM算法? 见问题3分析

【问题3: ESKF_LIO / funny_lidar_slam 算法对比 ★★】
  用户提问: 是否应该换成 ESKF_LIO 或 funny_lidar_slam?
  
  调研结论: Fast-LIO2 就是最优选择, 不需要换!
  
  ① ESKF_LIO (GitHub 284星)
     - 本质: Fast-LIO 1.0 的重新实现 (Error State Kalman Filter)
     - 同样使用 ikd-Tree, 但缺少 Fast-LIO2 的增量式更新优化
     - 定位精度和效率都不如 Fast-LIO2
     - 结论: 是Fast-LIO2的降级版, 没有任何理由切换
     
  ② funny_lidar_slam (GitHub 877星)
     - 多方法集成 (LOAM/NDT/ICP, 卡尔曼/优化)
     - 支持 Mid-360, 有回环检测
     - 但: SLAM定位精度不比Fast-LIO2好, 回环检测在小场景无用
     - 它展示的"大地图"是 PCD 点云, 不是 OctoMap
     - 结论: 功能更多但核心SLAM不如Fast-LIO2
     
  ③ Fast-LIO2 (GitHub 3700+星, 我们在用)
     - LiDAR-惯导紧耦合里程计的标杆
     - ikd-Tree增量式更新, 10Hz实时性能
     - 在我们的仿真中SLAM定位完全正常, 20Hz稳定输出
     
  关键认知: 别人用其他算法建的"大地图"是 PCD 点云文件,
    不是实时OctoMap! 点云只是堆叠扫描数据, 没有八叉树开销。
    Fast-LIO2 的 /cloud_registered 点云输出同样优秀。
    瓶颈在 OctoMap Server, 不在 SLAM 算法!

【问题1+4: OctoMap建图墙壁瓦解消失 + 大地图性能 ★★★ 核心修复】
  现象: 建图时两侧黄瓜行OctoMap看起来像完整墙壁, 但飞过去之后
        那面"墙"就开始瓦解消失, 飞远后残破不堪
        同时飞行一段时间后OctoMap停止更新(性能问题)

  根因 (终于找到!): OctoMap 射线模型(beam model)的miss更新!
    OctoMap对每个点做射线追踪: 从传感器原点到目标点
    - 射线终点(激光打到的地方) → hit更新 → 占据概率↑
    - 射线路径上(穿过的体素) → miss更新 → 占据概率↓
    
    当无人机飞过一面墙后, 新的激光射向更远的目标,
    射线会穿过之前建的墙 → 每次穿过都做miss更新(0.35) →
    多次miss后概率降到阈值以下 → 墙壁"瓦解消失"!
    
    同时 max_range=20m 导致射线追踪距离太长 → 性能差

  修复方案 (三管齐下):
    1. ★ max_range: 20m → 5m
       - 射线只追踪5m! 飞过5m之后, 射线根本够不到之前的墙
       - 已建的墙不会被miss更新擦除 → 完美保持!
       - 同时: 射线短 → 每帧计算量大幅下降 → 性能提升
    2. ★ miss: 0.35 → 0.48 (接近中性值0.5)
       - 即使5m内有射线穿过, miss的擦除效果也微乎其微
    3. 参数调优:
       - hit:  0.85 → 0.9  (占据更快建立)
       - min:  0.12 → 0.25 (占据概率不会降太低)
       - max:  0.97 → 0.99 (占据概率上限更高)
       - 降频: 2Hz → 1Hz  (更多处理时间)

  为什么之前的修复不管用?
    - 第十二次只做了: 降频+增大分辨率+减小max_range到20m
    - 但 max_range=20m 仍然太大, miss=0.35 仍然太激进
    - 这次直接把 max_range 降到 5m + miss 接近 0.5 = 标本兼治

  网上视频那些大地图怎么做的?
    - 大多数展示的是 PCD 点云(无八叉树开销, 纯堆叠)
    - 要做大型 OctoMap 必须: 短射线 + 弱miss + 低频输入
    - 这就是本次修复的方案

========== 关于定位方案的决策 ==========

  调研结论: 室内大棚定位用 光流+测距仪 (不用视觉定位)

  原因:
    1. 真机硬件: MTF-01P 光流测距一体模块 → 仿真应匹配
    2. 光流定位: 适合低空(<8m)、有纹理地面 → 大棚地面OK
    3. 测距仪定高: 1D激光, 精度高(<5cm), 不受气压影响
    4. 视觉定位(SLAM→PX4): 虽然精度更高, 但:
       - PX4 v1.14.3 参数支持不完善
       - 增加系统复杂度
       - 与真机方案不匹配(不用深度相机定位)
       - Fast-LIO2 SLAM 建图和飞控定位是独立的, 互不干扰

  EKF2融合架构:
    IMU(加速度+角速度) ─┐
    光流(水平速度)    ─┤→ EKF2 → 位置/速度估计 → 飞行控制
    测距仪(垂直距离)  ─┘

【问题: min=0.51 导致 OctoMap 整个空间被方块填满】

★ 第十五次修复的严重副作用:
  sensor_model/min=0.51 (高于 occupied_threshold=0.5) 的本意是:
  "一旦体素被标记为占据就永远不会变自由 → 防止墙壁瓦解"
  
  但实际效果是灾难性的:
  - LiDAR点云中不可避免存在噪点/散射/多径反射
  - 地面上的每一个点也会触发占据标记
  - 只要一个噪点落在自由空间的体素内, 该体素立刻变成"占据"
  - 由于 min=0.51 > 0.5, miss更新最低只能降到0.51 → 噪点无法被清理!
  - 结果: 每一帧点云都会新增大量永久性的噪声体素
  - 最终: 整个空间全部被彩色方块填满 (包括走廊/通道), 无法飞行
  
  ★ 教训: 防止墙壁瓦解不能通过让所有占据"不可逆"来实现,
  因为这同时让噪点也不可逆!

★ 第十六次正确修复: "强hit + 极弱miss" 平衡策略
  核心思路: 不是禁止概率下降, 而是让占据概率极难被侵蚀
  
  OctoMap 概率更新机制 (log-odds模型):
    hit:  log-odds += logit(hit_prob)   (正值, 增加占据概率)
    miss: log-odds += logit(miss_prob)  (负值, 降低占据概率)
  
  参数设计:
    hit=0.9  → logit = log(0.9/0.1)  = +2.20 (强占据证据)
    miss=0.47 → logit = log(0.47/0.53) = -0.12 (极弱自由证据)
    min=0.12 (默认值, 允许噪点被完全清理)
    max=0.97 (默认值, 占据概率上限)
  
  数学分析:
    一面墙被击中N次后, 概率被max钳位在0.97 (logodds=3.48)
    要把墙壁从0.97降到低于0.5(变成自由), 需要:
      3.48 / 0.12 = 29次连续miss更新
      在2Hz频率下 → 需要约14.5秒的射线连续穿过同一个体素
      实际中射线不可能持续穿过同一体素这么久 → 墙壁非常稳固
    
    一个噪点被击中1次后, logodds=2.20:
      2.20 / 0.12 = 18次miss更新即可清理
      在2Hz频率下 → 约9秒后噪点自动消失 → 自由空间保持干净

修改文件:
  launch/slam_mapping.launch:
    - sensor_model/miss: 0.49 → 0.47 (极弱自由空间标记, hit/miss比 18:1)
    - sensor_model/min: 0.51 → 0.12 (★恢复默认! 允许噪点被完全清理)
    - sensor_model/max: 0.99 → 0.97 (恢复默认)
    - 其余保持: max_range=15.0, hit=0.9, 2Hz

  OctoMap问题历史总结:
    第7-12次: 大地图建不了 (参数未优化, max_range太大导致太慢)
    第13次: max_range 20→5m (错误! 只能建5m范围)
    第14次: 分析替代方案, 未改参数
    第15次: min=0.51 (错误! 空间全部填满)

【问题1: OctoMap墙壁瓦解/建不了大地图的真正根因 — TF配置错误!】

  ★ 经过第7-16次反复调参(hit/miss/min/max/max_range), OctoMap问题从未彻底解决。
  根本原因不在参数, 而在TF (坐标变换):

  之前的数据流:
    Fast-LIO2 → /cloud_registered (frame_id=camera_init, 全局坐标系)
    → nan_filter → /cloud_filtered (frame_id=camera_init)
    → throttle → /cloud_throttled (frame_id=camera_init)
    → OctoMap (frame_id=camera_init)
  
  OctoMap收到点云后需要做射线追踪:
    - 从传感器位置(sensor origin)到每个点, 沿途标记自由空间(miss), 终点标记占据(hit)
    - sensor origin = TF查找: 点云frame_id → OctoMap frame_id 的变换的平移部分
    - 当点云frame_id = camera_init, OctoMap frame_id = camera_init 时:
      sensor origin = TF(camera_init → camera_init) = (0, 0, 0) !!
    
  ★ 所有射线都从世界坐标原点(0,0,0)出发, 而不是无人机当前位置!
  
  后果:
    - 无人机在x=0附近时: 射线长度合理, 建图正常
    - 无人机飞到x=5时: 射线从(0,0,0)出发到x=5处的点, 路径上穿过5m的空间
    - 每条射线穿过之前建好的墙壁 → 大量错误miss更新 → 墙壁瓦解!
    - 飞得越远, 射线越长, 穿过的墙壁越多 → "建到后面就建不了了"
    - 无论怎么调 hit/miss/min/max 参数都无法根治, 因为问题在sensor origin!

  之前的静态TF还存在冲突:
    MAVROS发布: odom → base_link
    Fast-LIO2发布: camera_init → body
    静态TF: odom→map→camera_init→body→base_link
    → 形成从odom到base_link的两条路径 = TF树冲突!

  修复:
    ① nan_filter改为订阅 /cloud_registered_body (frame_id=body)
       - FAST-LIO2 的 scan_bodyframe_pub_en=true 会发布此话题
       - 点云在body帧, OctoMap通过TF(body→camera_init)得到正确的无人机位置
       - sensor origin = 无人机实际位置 → 射线追踪正确!
    
    ② 移除冲突的静态TF:
       - 删除 body→base_link (消除第二条路径到base_link)
       - 删除 odom→map (消除TF树环路)
       - 保留 map→camera_init (RViz显示需要)
       - TF树变成两棵独立树: SLAM树(map→camera_init→body) + MAVROS树(odom→base_link)

问题2: 航线规划速度慢原因
========================

A*路径规划慢的核心原因 (不需要修改代码, 仅解释):

1. 栅格分辨率高 → 搜索空间巨大
   地图: 1132×408 = 461,856 个栅格 (分辨率0.05m)
   规划一段20m路径需要遍历 ~400个栅格节点

2. Python解释器效率低
   Python 做循环/字典操作比 C++ 慢 50~100倍
   A* 每次扩展需要: heapq操作 + 字典查询 + 碰撞检测

3. 原有碰撞检测极其低效 (已在本次修复)
   旧: 每扩展1个节点, 检查 safety_margin 圆内 ~113 个栅格
   新: 预膨胀后只需 O(1) 数组查表

修复后规划速度预期提升 10~50 倍 (消除碰撞检测的Python循环)

如需进一步提速:
  - 降低地图分辨率 (pcd_to_2d_map.py --resolution 0.10)
  - 改用C++实现的规划器 (如 nav_core/global_planner)

========================
修复1: EKF2参数名不匹配 ★关键修复
========================

【问题根因】

PX4 v1.14.3 对EKF2参数进行了重命名, 旧参数名在运行时不存在:
  EKF2_HGT_MODE → EKF2_HGT_REF    (高度参考源)
  EKF2_RNG_AID  → EKF2_RNG_CTRL   (测距仪控制模式)
  EKF2_AID_MASK (bit1=光流) → EKF2_OF_CTRL (光流独立开关)

configure_ekf2.py 一直使用旧参数名, 导致所有EKF2配置失败!

【严重后果】
  全部参数失败 → PX4 使用默认值:
    EKF2_HGT_REF = 1 (GPS高度)  → 大棚无GPS → 无高度参考!
    EKF2_OF_CTRL = 0 (光流禁用)  → 无水平位置参考!
    EKF2_RNG_CTRL = 1 (条件模式) → 测距仪仅起降时启用
  → 无人机完全没有位置/高度估计 → 无法起飞/只在地面转!

这也解释了第14次以来反复出现的起飞问题!

【修复方案】

文件: scripts/configure_ekf2.py (完全重写)
  新增功能:
    1. 参数就绪检测: 先读取已知参数(SYS_AUTOSTART)确认PX4参数系统就绪
    2. 兼容双名称: 先尝试新名称, 失败后尝试旧名称
       EKF2_HGT_REF (新) → EKF2_HGT_MODE (旧) = 2 (测距仪)
       EKF2_RNG_CTRL (新) → EKF2_RNG_AID (旧) = 2 (始终启用)
    3. 新独立光流开关: EKF2_OF_CTRL = 1 (启用光流)
    4. 重试机制: 每个参数最多重试3次
    5. 同时设置旧版EKF2_AID_MASK=2作为兼容 (某些版本仍需要)
  
  参数值:
    EKF2_HGT_REF = 2     (高度源: 测距仪)
    EKF2_RNG_CTRL = 2    (测距仪始终启用, 非仅起降)
    EKF2_OF_CTRL = 1     (启用光流定位)
    EKF2_RNG_A_HMAX = 8.0  (测距仪最大高度)
    EKF2_RNG_NOISE = 0.05  (测距仪噪声)
    EKF2_RNG_A_VMAX = 2.0  (测距仪最大垂直速度)

    - 这样用户可以点击地图上任意XY位置来放置航点

    gnd = Marker()
    gnd.ns = "ground_plane"
    gnd.type = Marker.CUBE
    gnd.pose.position.z = -0.05
    gnd.scale.x = 200.0; gnd.scale.y = 200.0; gnd.scale.z = 0.1

【问题: roslaunch 报 "Resource not found: px4"】

  现象:
    # 不 source 直接运行 → 找不到包
    $ roslaunch mak4_sim_cpp mak4_greenhouse.launch
    RLException: [mak4_greenhouse.launch] is neither a launch file in package [mak4_sim_cpp]

    # source 之后 → 找不到 PX4
    $ source ~/catkin_ws_cpp/devel/setup.bash
    $ roslaunch mak4_sim_cpp mak4_greenhouse.launch
    Resource not found: px4

  根因:
    catkin 的 setup.bash 会 **重置** ROS_PACKAGE_PATH。
    .bashrc 中虽然在 catkin_ws 之后追加了 PX4 路径，
    但用户手动 source catkin_ws_cpp/devel/setup.bash 时，
    ROS_PACKAGE_PATH 被覆盖为仅包含 catkin_ws_cpp/src + /opt/ros/noetic/share，
    PX4-Autopilot 路径丢失 → $(find px4) 失败。

  修复方案:
    修改 ~/.bashrc，将 PX4 环境设置封装为函数 setup_px4_env()，
    并创建两个快捷命令 use_cpp / use_py:

      setup_px4_env() {
        source $PX4_HOME/Tools/simulation/gazebo-classic/setup_gazebo.bash ...
        export ROS_PACKAGE_PATH=$ROS_PACKAGE_PATH:$PX4_HOME:...
      }
      alias use_cpp='source ~/catkin_ws_cpp/devel/setup.bash && setup_px4_env'
      alias use_py='source ~/catkin_ws/devel/setup.bash && setup_px4_env'

【正确的启动方式】

  # Python 工作空间 (默认, 新终端自动生效):
  roslaunch mak4_sim mak4_greenhouse.launch

  # C++ 工作空间 (需要先切换):
  use_cpp
  roslaunch mak4_sim_cpp mak4_greenhouse.launch

  # 切回 Python 工作空间:
  use_py
  roslaunch mak4_sim mak4_greenhouse.launch

  ⚠️ 注意: 每个终端只能用一个工作空间!
  ⚠️ 不要直接 source setup.bash, 要用 use_cpp / use_py 快捷命令!

【修复1: 键盘遥控 R→W 不停上升 + 高度不稳定】

  问题现象:
    - 按R上升后按W前飞, 无人机仍然继续上升 (边升边飞)
    - 飞行中高度不稳定, 忽高忽低

  根因:
    1) 按键互不清零: R键只设 vz=0.3, 不清除 vx/vy;
       W键只设 vx=0.5, 不清除 vz → vz残留导致持续上升
    2) 纯速度模式: vz=0 时依赖PX4速度控制器保持高度,
       但光流+测距仪的EKF2融合在速度模式下有微小漂移

  修复方案:
    a) 所有按键现在清零全部轴的速度:
       - WASD/QE: 同时设 vz=0 (不再残留垂直速度)
       - R/F: 同时设 vx=vy=yr=0 (纯垂直运动)
    b) 引入混合控制 (setpoint_raw/local + PositionTarget):
       - 水平运动: 用速度控制 (velocity XY)
       - 垂直保持: 用位置控制 (position Z) ★关键
       - 当vz=0时, 自动锁定当前高度作为Z轴位置目标
       - 当按R/F时, 切换为全速度模式 (垂直运动)
       - 按其他键时, 记忆当前高度进行位置锁定

  修改文件:
    keyboard_teleop.py           — 重写 send_command(), 用 setpoint_raw/local
    keyboard_teleop_node.cpp     — 同样重写 sendCommand()

  技术细节:
    话题:  /mavros/setpoint_raw/local (mavros_msgs/PositionTarget)
    定高 type_mask = 1507:
      IGNORE_PX | IGNORE_PY | IGNORE_VZ | IGNORE_AF* | IGNORE_YAW
      → 使用 velocity.x/y (速度XY) + position.z (位置Z) + yaw_rate
    升降 type_mask = 1479:
      IGNORE_PX | IGNORE_PY | IGNORE_PZ | IGNORE_AF* | IGNORE_YAW
      → 使用 velocity.x/y/z (全速度) + yaw_rate

【修复2: 起飞时无人机在地面旋转 (C++ & Python)】

  问题现象:
    执行 "start" 后无人机在地面上持续旋转, 无法正常起飞

  根因:
    PRE_ARM 和 TAKING_OFF 阶段调用 sendSetpoint(cx, cy, alt) 时 yaw=NAN
    yaw=NAN 时 orientation.w=1.0, 相当于强制 yaw=0
    如果无人机当前朝向不是0度, PX4在地面尝试旋转到0度, 导致原地转圈

  修复 (C++):
    (1) 添加 getCurrentYaw() 辅助函数 (从四元数提取yaw)
    (2) PRE_ARM: sendSetpoint(cx, cy, alt, getCurrentYaw())
    (3) TAKING_OFF: 同上

  修改C++文件:
    grid_map_planner_node.cpp, patrol_planner_node.cpp

  修复 (Python):
    (1) 添加 _get_current_yaw() 方法
    (2) PRE_ARM/TAKING_OFF 调用时传入当前yaw

  修改Python文件:
